# OMP compatibility contract (authoritative)

This is an OMP port of omo 5.1.19. The workflow activates only on an explicit request for its named mode (or an explicit request to perform that specialised workflow); bare ULW does not activate planning, looping, execution, saturation research, or mass orchestration. Host and current user instructions outrank this skill. The native behavioural doctrine remains below; this contract replaces harness-specific machinery.

## Native delegation and orchestration

Read the current task schema before dispatch. Supply shared goal and interface constraints in top-level context, and independent assignments in tasks. Include the concise intent field when the exposed schema requires it; eval tool proxies may supply that field. Each entry requires task (the self-contained assignment) and solutionSpace (how fixed or open the solution is, not file scope or workload size). Put exact read/write paths, non-goals, prescribed steps and observable acceptance in task, with TASK / DELIVERABLE / SCOPE / VERIFY / STOP WHEN or the equivalent # Target / # Change / # Acceptance sections. Do not repeat shared context or sibling coordination in solutionSpace. Large shared material belongs in a local:// artifact referenced by literal path, not pasted into every child.

name is optional; when supplied use a unique CamelCase name of at most 32 characters. Omit agent for the default task worker; never send agent: "task". Select only listed specialists: scout for exploratory read-only discovery, sonic for already-decided mechanical work, senior-task for difficult implementation/investigation when available, reviewer or security-reviewer for reviews that accept their native response format. For a workflow-specific JSON receipt, omit agent and specify the read-only review charter in task; task text cannot override a specialist's fixed output contract. Difficulty and specialty labels such as quick, deep or architect are planning metadata to map to these roles, never callable agent names or task fields. OMP owns each role's model/fallback routing: do not send model, category, subagent_type, prompt or run_in_background. Record the requested tier and selected role before dispatch, then the resolvedModel/identity/thinking reported by the actual result; never record a planned model as the one that ran. If a required model cannot be selected through the exposed contract, report that capability gap rather than inventing a pin.

The current task entries expose task, solutionSpace, name, agent and tools. Do not pass outputSchema or schemaMode unless a future exposed schema explicitly adds them. tools names eval-defined tools; it is not an arbitrary built-in tool allowlist. Respect the host's mid-flight check policy: read covering tests and capture the required reproduction first, then run final build/lint/tests once when the change is ready, not repeatedly during unrelated steps. Completion still requires the assigned checks and independently verified evidence. Children start blank; put every task-specific fact and required skill path in the assignment.

Tool names in a brief are canonical host names only: bash, read, edit, write, grep, glob, eval, task, wait, todo, ask. The parent may see prefixed internal aliases (for example `mcp__…__open_bash`, `brass_grep`, `palm_edit`, `audit_eval`); never copy those into a brief, because the child cannot call them (2026-10-13: 30+ failed child calls to invented names). Size every child for one run of about 45 minutes and one file bundle plus its check so its context stays under roughly 200k tokens; a child that outgrows that returns a partial result with its changed paths, and the lead re-dispatches the remainder as a fresh task. Workers change files only with edit/write, never with bash `sed -i` or script rewrites, and never stage or commit; the host injects an `<omo-ulw-worker>` block into every child restating these limits.

Communicate by write to agent://<actual-agent-id> with content; never invent an id, team, or recipient. Read agent://<id> for one needed midpoint decision; native wait wakes on a settled result or message (see Background results and recovery). No team API is available: a cooperating roster is native background children with the lead relaying discoveries and owning durable shared state. One cohesive change is one worker; run workers in parallel only when their files, state and proof are disjoint. Every dispatch names its allowed write paths; serialize overlapping write paths (or use separately owned worktrees when the checkout is shared or branch/commit delivery was explicitly authorised; never commit to manufacture isolation). The lead keeps product implementation delegated but MAY run independent real-surface QA and integration checks itself. Each worktree has one stage/commit owner (default the lead) who stages explicit owned paths only: no `git add -A` or unscoped stage while another worker's or the user's WIP is present. To cancel, read the actual runtime cancellation contract; do not invent a cancellation method, use elapsed time as a reason, or abandon a pending handle.

For a DAG, first read xd://eval/agents if available and use only the documented native workpool surface. If unavailable, use explicit dependency waves through task/wait; no workflow SDK is needed. See ../../mass-ulw/SKILL.md from a references directory (or ../mass-ulw/SKILL.md from a skill root). Completed outputs remain durable and verified; failed nodes block only descendants, unrelated branches continue. Retry the failed node with its exact failure, retain unchanged completed nodes, invalidate changed nodes and their transitive dependents, and record every attempt.

## Background results and recovery

Task returns actual child ids immediately. Record a live pending set keyed by those actual handles (plus any job or watch handle the host actually returned) and work independently. A terminal result (success, failure or cancellation), whether auto-delivered or collected by wait, removes only its own handle; record its outcome and keep every other sibling pending. Native wait({}) is a wake on the first settled result, message or steering interrupt, not a whole-wave barrier and not a function accepting child handles; no filtered-wait or list-jobs API exists, so never invent one. A first result, a message or a still-running snapshot is not whole-wave completion. Call wait only when the next action is blocked on a result still in the pending set; when the set is empty, do not call it, and never loop empty waits. If every remaining pending item is auto-delivery-owned and wait cannot target it, finish independent work, then end the turn and await the notification. A downstream node starts only after every dependency has terminal success and independently verified evidence; final delivery requires an empty pending set. The eval helper wait(handles) is a separate documented wave-barrier API, not the native wait tool.

Keep two kinds of pending verification apart. A period-defined observation (a scheduled/cron run at a stated time, an "N days stable" or soak window) is satisfied only by the period or event itself: record the evidence-backed end condition and stay waiting; never shorten the window or let an early check stand in for it. A runnable same-entrypoint check (for example the exact command the cron job runs, executed now) is a separate runnable audit: run it now when the existing permission, duplicate-run, external-write and spend boundaries allow, and record it as an audit, not as the observation; if a boundary blocks it, record that boundary and hold. Neither is a reason to call wait on an empty pending set. Neither authorises an external message: a Slack/email/chat send or any other external write stays held until the user explicitly approves it, even if the command that would produce it is otherwise runnable.

Korean handoffs: when the user writes Korean, the first sentence of each progress report or handoff states, in order, (1) the completed result, (2) what is currently waited on (implementation, CI, observation or approval), (3) the evidence-backed end condition or time, and (4) the next action, for example "완료: …; 대기: CI; 종료 조건: …; 다음: …". Include only what the user needs. Report by phase or event; never invent an ETA, imply a timer daemon, or state a time the evidence does not give. Boulder status enum values stay unchanged; explanations belong in the existing ledger and report, not in new statuses.

Record actual returned identity and terminal status, without inventing absent metadata. Put required receipt fields or a JSON schema in the task text and validate the actual terminal response from task/wait or agent://<actual-id>. Use structured.data and parsed field selectors only when actually returned by the runtime; a preview, message or running snapshot is not completion. Missing or invalid required fields fail the output contract. Freeform reports may request the following JSON shape, with all headings, citations and EXPAND tails inside report.

```json
{"type":"object","properties":{"report":{"type":"string"}},"required":["report"],"additionalProperties":false}
```

Recovery is lead-owned state plus native actions, not workflow retry/amend/send APIs. For a failed terminal node, retain verified siblings, record the failure and attempt, then spawn a fresh task with failure context and bind its new actual id to the same logical node. A changed definition invalidates that node and its descendants; preserve unchanged verified nodes. Steer a live or idle child through supported agent:// messaging, or a documented AgentHandle.send; a successful send is not a new completion receipt. Reconcile the resulting run before accepting its next result. Do not duplicate live writers; cancel only through the documented native route and collect its terminal state before replacement. Use workpool only through the methods documented in xd://eval/agents; it does not provide graph retry/amend operations.

## Planning choices and authorization channels

Use native blocking ask from the main session for material planning choices and explicit plan-creation decisions after independent work is finished; use only its exposed parameters. Put the context the user needs to decide (the state, the options and the consequence of each) inside the ask panel itself, not only in earlier chat. Follow host instructions requiring direct permission requests. A timed-out, dismissed, empty or unavailable answer never grants approval or authorizes an irreversible, destructive or spend action, even when a tool suggests proceeding on best judgment. Default only reversible ordinary forks. At a planning approval gate keep `status: awaiting-approval`, write no plan and stop; if ask is unavailable, state that once and await an explicit decision in chat. An explicit no-plan ulw-execute bootstrap already authorizes generating its prerequisite plan, so do not add another generic approval gate there.

## Durable binding goal and evidence

OMP has no goal SDK or goal tool. Record the binding objective, criteria, constraints and WHEN TO STOP in durable files through read/write/edit before execution. This is the canonical no-goal-tool fallback, not an optional notepad substitute. The lead is the single writer of goal/criteria/ledger state; workers return evidence and cannot safely append concurrently. Read existing state first, preserve its bytes, append ledger entries via edit (or read + write with single ownership), observe the result and read back. No hidden locks, atomic compare-and-swap service, env session binding, or automatic continuation is assumed. Resume from files and actual agent handles after compaction; do not recreate completed work.

Use OMP todo for every registered action and cleanup resource, updating transitions immediately using its actual schema. With parallel children, the lead's current orchestration step can be the single in-progress todo while per-lane states are durable; do not misreport parallel work as completed. Missing artifacts, inconclusive verdicts, or stale proofs block completion.

Bind evidence to tracked tree AND working diff/untracked inputs: HEAD tree alone does not prove uncommitted edits. Record the capture revision, working-content digest or diff, invocation, result, nonempty artifact paths, adversarial cases and cleanup. A changed captured input invalidates dependent proofs; a metadata-only rebase retaining identical content does not. Never relabel old evidence to a new tree.

## Host permissions and real surfaces

Planning approval authorizes plan creation only, never implementation. Explicit execution activation authorizes implementation on a feature branch (the plan's `## Commit strategy` branch, or a worktree when the checkout is shared); creating or switching to that branch needs no authorization, editing `develop`/`main` directly is never allowed, and no commit is authorized unless the user asked for commits. Inspect history and stage only owned files once commits are authorized; otherwise record no-commit: user has not authorized commits and report the branch name and uncommitted file count in the handoff. Worktrees/landing do not bypass this: do not commit, merge, push, open a PR, send external messages, deploy, delete user work, or rewrite history without the applicable explicit user authorization. --make-pr and --ship carry only the explicit scope the user gave; resolve any missing commit/merge authorization at the last gated step after local deliverables and evidence are ready. Preserve dirty user changes. Unrelated defects are local findings, not automatically published issues.

Follow the exposed browser tool contract before real-surface QA; read skill://cua-driver when using its browser or desktop route. Use actual session browser/GUI tools, never unshipped browser engines, a copied login profile, fictional script/qa paths or nonexistent skill names. HTTP uses the live endpoint; CLI/data uses real stdout/state; visual TUI proof needs a real rendered terminal, not capture-pane for colour/layout/CJK. If that renderer is absent, record a capability blocker rather than fake evidence. Browser/page QA includes desktop/mobile, paginated output includes EVERY rendered page. Only tear down task-owned resources, with receipts. Start long commands and condition watches with native async bash; add each returned handle to the pending set, let its result auto-deliver, and call wait only when blocked on it; no sleeping or status-poll loops.

Ask is blocking in OMP. Research collection must start before any unresolved format interview; state destination-derived defaults with a visible veto and continue independent collection, then ask a genuinely blocking question only after independent work is done. Do not pass waitForAnswer:false or invent asynchronous question tools. recall/retain are the available memory interface: recall qualified preference episodes, retain observed/declared episodes with provenance; paths named by the original memory doctrine are logical topics, not required filesystem or memory APIs.
